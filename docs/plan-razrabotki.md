# План разработки: DevBoard — веб-приложение для управления личными проектами программиста

**Тема проекта:** Разработка веб-приложения для управления личными проектами программиста с учётом задач, сроков, технологий и прогресса

**Название системы:** DevBoard (зафиксировано по макету)
**Дата отсчёта:** 14 октября 2026 (среда)
**Целевая сдача:** начало ноября 2026 → рабочий срок **≈ 18–21 день** (бюджет ~90–110 часов при 5–6 ч/день)

---

## 1. Главное: объём нужно сократить и согласовать

В ТЗ 15 модулей и 12 таблиц — это объём полноценной системы (уровень Jira/YouGile в миниатюре), а не работа на три недели. Чтобы сдать в срок, объём фиксируется **сейчас**, а не «как получится».

| Уровень | Модули | Решение |
|---|---|---|
| **MVP — ядро сдачи** | 1–8 (авторизация, проекты, задачи, Kanban, стек, сроки, прогресс, дашборд) | Реализуем полностью: API + UI + тесты. Это то, что защищается как «работает» |
| **Расширение** | 10 (учёт времени), 12 (история), 13 (заметки), 14 (аналитика) | Реализуем после закрытия MVP. Режутся в этом порядке при отставании |
| **Опционально** | 9 (GitHub), 11 (уведомления) | 11 — только внутрисистемный список уведомлений (без email/пушей). 9 — read-only синхронизация через GitHub API |
| **Демо (вне MVP)** | 15 (ИИ-помощник) | 1 endpoint: декомпозиция задачи на подзадачи через LLM API. Модуль помечен «Дополнительно» — в отчёт как развитие проекта |
| **Вне рамок** | — | Мобильное приложение, командная работа и роли, реальная отправка email/SMS, CI/CD в прод |

**Что сделать в первую очередь:** согласовать эту таблицу с руководителем. Если он требует все 15 модулей в полном объёме — срок начала ноября нереален, и это лучше выяснить сейчас, а не 30 октября.

**Развилки по срокам:**
- Сдача 1–3 ноября → «Расширение» подтягиваем до 30 октября, 31 окт – 2 ноя только документация и презентация.
- Сдача после 5 ноября → добавляем GitHub-синхронизацию и аналитику в полном виде.

## 2. Целевой стек

**Backend:** Python 3.12, FastAPI, SQLAlchemy 2.0 (async) + Alembic, Pydantic v2, PostgreSQL 16, asyncpg, Argon2 (хеширование паролей), PyJWT, httpx, APScheduler, pytest + httpx.AsyncClient, ruff.

**Frontend:** React 18 + TypeScript + Vite, React Router, собственные стили на CSS-переменных (дизайн-токены) и собственный набор SVG-иконок — без внешних UI-библиотек. Добавляются по мере необходимости: dnd-kit (Kanban drag-and-drop), TanStack Query (работа с API), react-hook-form + zod (формы).

**Инфраструктура:** Docker Compose (api + db + frontend + scheduler), .env, Swagger/OpenAPI из коробки.

> Обоснование выбора FastAPI + PostgreSQL + React оставляем как в ТЗ: миграция на Django/Node.js ради этого проекта не даёт выигрыша, а стоит времени.

## 4. Ключевые технические решения (фиксируем заранее)

**Авторизация и безопасность (модуль 1).** Access-токен JWT живёт 15 минут, refresh-токен — 30 дней, хранится в HttpOnly + Secure + SameSite=Lax cookie. Обязательна **ротация refresh-токена** с отзывом старого (иначе требование «корректное обновление токенов» не выполняется) → нужна таблица `refresh_tokens`. CSRF защищаем схемой double-submit: сервер кладёт CSRF-токен в отдельную cookie, клиент дублирует его в заголовке `X-CSRF-Token`, сервер сверяет. Пароли — Argon2id, не SHA-256 и не bcrypt без параметров.

**Проверка прав доступа.** В личной ИС ролей нет — есть **ownership-scoping**: каждый запрос фильтруется по `user_id` из токена, а не по id из тела/URL. Это закрывается одной зависимостью FastAPI + проверкой в сервисном слое. Именно это проверяют на защите, когда спрашивают «проверка прав доступа».

**Расчёт прогресса (модуль 7).** Прогресс проекта = доля закрытых задач от общего числа, но подзадачи не должны считаться дважды: считаем только листья дерева задач либо задачи верхнего уровня. Формула выносится в один сервис и переиспользуется в дашборде, карточке проекта и отчётах.

**Kanban (модуль 4).** Колонки = записи `task_statuses` (To Do / In Progress / Done), а не хардкод во фронтенде. Перемещение — отдельный endpoint `PATCH /tasks/{id}/move` с полем позиции (`order_index`), иначе после drag-and-drop порядок задач не сохранится. Порядок в колонке — разреженные индексы, чтобы не переписывать все строки при каждом переносе.

**Контроль сроков (модуль 6).** Просроченные задачи — не отдельная таблица, а запрос с индексом по `due_date`. Календарь — представление месяц/неделя на фронтенде по данным задач проекта.

**История изменений (модуль 12).** Дешевле всего делать сразу: единая функция логирования в сервисном слое, которая пишет `user_id, entity_type, entity_id, action, changes (JSONB), created_at`. Если заложить её на второй неделе — она покроет все модули; если пытаться «дописать» в конце, придётся лезть в каждый роутер.

**GitHub (модуль 9).** Только чтение через REST/GraphQL API с personal access token пользователя. Коммиты нельзя использовать как метрику качества кода — это фиксируется в тексте записки как осознанное ограничение интерпретации.

**Уведомления (модуль 11).** APScheduler раз в час ищет задачи с дедлайном в ближайшие 24–48 часов и пишет записи в `notifications`. UI показывает счётчик в колокольчике и список. Реальная отправка писем — вне объёма.

## 5. Уточнения к схеме БД (важно!)

Присланные 12 таблиц — хорошая база, но под заявленные модули их **не хватает**. Минимально нужно 17:

| Что добавить | Зачем |
|---|---|
| `notes` | Модуль 13 (заметки и документация) в списке таблиц отсутствует, хотя модуль заявлен |
| `refresh_tokens` | Без хранения refresh-токенов нет их отзыва и ротации → требование «корректное обновление токенов» не выполнено |
| `password_reset_tokens` | Восстановление пароля (модуль 1) — иначе восстанавливать нечем |
| `git_activities` + `task_git_activities` | Коммиты, ветки и pull request'ы (модуль 9) в одной таблице с полем `type` + связь с задачами многие-ко-многим |

Также уточнить поля в уже заявленных таблицах:
- `tasks`: `parent_task_id`, `order_index`, `estimated_hours`, `completed_at`
- `activity_logs`: `entity_type`, `entity_id`, `action`, `changes JSONB`
- `time_entries`: `task_id`, `user_id`, `started_at`, `ended_at`, `minutes`, `comment`
- `projects`: `status` (active/paused/archived), `archived_at`, `due_date`

Полная схема с полями, связями и индексами — в документе `tz-devboard.md`, раздел «Требования к данным».

Итог для записки: **один пользователь → много проектов → много задач (самоссылочная иерархия) ; технологии ↔ проекты — многие-ко-многим через `project_technologies` ; задачи ↔ Git-активности — многие-ко-многим**.

## 7. Структура пояснительной записки

1. **Введение** — актуальность (разрозненность инструментов учёта задач), цель, задачи, объект и предмет, практическая значимость.
2. **Анализ предметной области и аналогов** — Jira, Trello, YouGile, Linear, Notion: таблица сравнения по функциям, вывод о нише (личные проекты программиста, привязка стека и Git).
3. **Требования к системе** — функциональные (таблица из ТЗ с приоритетами) и нефункциональные; карта экранов по макету.
4. **Проектирование** — архитектура (клиент → REST API → СУБД, слои), ER-диаграмма (17 таблиц), спецификация OpenAPI, описание модели прав доступа.
5. **Реализация** — обоснование стека, ключевые решения: авторизация с ротацией refresh и CSRF, ownership-проверки, Kanban с сохранением порядка, расчёт прогресса, интеграция GitHub API, фоновая задача напоминаний.
6. **Тестирование** — виды тестов, сценарии, результаты прогонов, найденные и исправленные дефекты.
7. **Развёртывание и эксплуатация** — Docker Compose, `.env`, инструкция запуска, резервное копирование БД.
8. **Анализ результатов** — сопоставление запланированного и фактического времени по задачам, оценка достижения цели.
9. **Заключение, список литературы, приложения** (листинги, скриншоты, диаграммы).

**Диаграммы:** use case (актёр-пользователь и функции), ER (БД), схема архитектуры, activity/BPMN для жизненного цикла задачи (To Do → In Progress → Done), sequence для авторизации и обновления токена, диаграмма Ганта по этапам. Инструменты: draw.io, PlantUML или Mermaid.

> Записку пишем **параллельно с кодом** (по 30–40 минут в конце каждого блока), а не отдельным этапом после. Иначе в конце останется неделя только на текст — и это самая частая причина незачёта.

## 8. Риски и снижение

| Риск | Что делать |
|---|---|
| Объём 15 модулей не влезает в 3 недели | Зафиксировать MVP (1–8) письменно и согласовать с руководителем **на этой неделе** |
| «Дописать» историю изменений и права доступа в конце | Заложить ownership-зависимость в Блоке 1, логирование — в Блоке 2 |
| Drag-and-drop теряет порядок после перезагрузки | Поле `order_index` + endpoint перемещения реализуем в Блоке 2, не позже |
| Дашборд съедает время: 6 блоков на одном экране | Собирать дашборд последним в Блоке 3, из уже готовых API-ответов, без новых запросов под каждый виджет |
| GitHub API упирается в лимиты и токены | Read-only, кэширование ответов, graceful degradation: без токена модуль просто скрыт |
| Документация «на последний день» | Пишем инкрементально по блокам, скриншоты снимаем сразу после каждой вехи |
| Сдача раньше, чем ожидалось | Режем «Расширение» в порядке: аналитика → GitHub → уведомления; учёт времени и заметки оставляем |
