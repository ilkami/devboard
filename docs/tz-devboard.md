# Техническое задание: DevBoard

**Наименование системы:** DevBoard — веб-приложение для управления личными проектами программиста

**Полное наименование темы:** Разработка веб-приложения для управления личными проектами программиста с учётом задач, сроков, технологий и прогресса

**Версия документа:** 1.0 от 14.10.2026
**Основание для разработки:** перечень модулей и требований из задания на проект; промо-макет целевого интерфейса DevBoard

---

## 1. Назначение и цели системы

**Назначение.** Единое рабочее место программиста, который ведёт несколько личных проектов параллельно: вместо разрозненных списков, заметок и блокнотов все проекты, задачи, сроки, стек технологий и прогресс находятся в одной системе.

**Цели разработки:**
- дать владельцу проектов наглядную картину «что сейчас в работе, что просрочено, насколько каждый проект продвинулся»;
- связать задачу с технологиями проекта и с реальными изменениями кода в Git;
- заменить субъективную оценку «работа идёт» измеримым показателем — долей выполненных задач и трудозатратами.

**Границы системы.** Система однопользовательская по модели данных: каждый пользователь видит только свои проекты. Многопользовательская совместная работа, роли и команды в объём не входят, но модель данных строится так, чтобы их можно было добавить без переделки схемы.

---

## 2. Пользователи и сценарии

**Единственный тип пользователя — владелец проектов (роль `owner`).** Регистрируется, ведёт свои проекты, работает только со своими данными.

**Основные сценарии:**
1. Регистрация → вход → создание первого проекта с указанием стека и дедлайна.
2. Добавление задач и подзадач, оценка времени, распределение по приоритетам.
3. Ежедневная работа: перетаскивание задач по Kanban-доске, отметка выполнения.
4. Контроль сроков: просмотр календаря и списка просроченных задач.
5. Просмотр дашборда: сколько всего проектов, средний прогресс, что в работе на этой неделе.
6. Возврат к задаче через неделю: чтение заметок и истории изменений по проекту.
7. Связывание задачи с коммитом и просмотр изменений кода по задаче.

## 4. Функциональные требования

Приоритеты: **О** — обязательно, **Ж** — желательно, **Д** — дополнительно.

### Модуль 1. Авторизация — приоритет О

| № | Требование | Критерий приёмки |
|---|---|---|
| 1.1 | Регистрация по email и паролю | Пользователь создан, пароль в БД хранится в виде хеша Argon2id, в ответе нет хеша |
| 1.2 | Вход в систему | Верная пара → access- и refresh-токены; неверная → 401 без раскрытия, что именно неверно |
| 1.3 | Обновление токенов | Refresh-токен одноразовый: при обновлении старый отзывается, выдаётся новый. Повторное использование отозванного токена отклоняется |
| 1.4 | Выход из системы | Refresh-токен отзывается в БД, cookie очищается |
| 1.5 | Восстановление пароля | Запрос письма не раскрывает, существует ли email; токен одноразовый, живёт 1 час; после смены пароля все refresh-токены отзываются |
| 1.6 | Защита от CSRF | Cookie-аутентификация сопровождается парой CSRF-cookie + заголовок `X-CSRF-Token`; несовпадение → 403 |
| 1.7 | Проверка прав доступа | Любой запрос фильтруется по `user_id` из токена. Попытка обратиться к чужому объекту (по id из URL) → 404, а не 403, чтобы не раскрывать существование объекта |
| 1.8 | Восстановление после перезагрузки | При истёкшем access-токене фронтенд автоматически обновляет его и повторяет запрос без потери действий пользователя |

## 5. Нефункциональные требования

**Безопасность**
- Пароли — Argon2id с солью; минимальная длина 8 символов.
- Access-токен JWT — 15 минут; refresh-токен — 30 дней, хранится в HttpOnly + Secure + SameSite=Lax cookie, ротируется при каждом обновлении.
- CSRF-защита по схеме double-submit для всех изменяющих запросов.
- Ограничение частоты: вход и запрос восстановления пароля — не более 5 попыток в минуту с одного адреса.
- Токены GitHub и любые секреты хранятся зашифрованными, в API никогда не возвращаются; секреты конфигурации — только в `.env`.
- Валидация всех входных данных схемами Pydantic; SQL-запросы — только через ORM с параметрами.

**Производительность**
- Типовой запрос API — до 300 мс при объёме до 1000 задач на пользователя.
- Пагинация списков по 20–50 записей; индексы по внешним ключам и полю срока.
- Исключение проблемы N+1 через жадную загрузку связанных объектов.
- Дашборд — один агрегированный запрос вместо нескольких.

**Совместимость и интерфейс**
- Поддержка Chrome, Firefox, Safari последних версий; минимальная рабочая ширина 1280 px.
- Для каждого списка предусмотрены состояния: загрузка (скелетон), пусто (подсказка с действием), ошибка (сообщение и повтор).
- Язык интерфейса — русский; формат дат — ДД.ММ.ГГГГ.

**Развёртывание**
- Запуск одной командой `docker compose up` на чистой машине.
- Миграции БД — Alembic, автоматически при старте; сиды справочников и демо-данных отдельной командой.
- Документация API — Swagger/OpenAPI, доступна по `/docs`.

### Связи

- `users` 1 → N `projects`; `projects` 1 → N `tasks`; `tasks` 1 → N `tasks` (самоссылочная иерархия подзадач).
- `projects` N ↔ N `technologies` через `project_technologies`.
- `tasks` N ↔ N `git_activities` через `task_git_activities`.
- `tasks` 1 → N `time_entries`; `projects` 1 → N `milestones`, `repositories`, `notes`.

### Индексы

`tasks(project_id)`, `tasks(parent_task_id)`, `tasks(status_id)`, `tasks(priority_id)`, `tasks(due_date)`, `tasks(project_id, order_index)`, `projects(user_id, status)`, `time_entries(task_id)`, `notifications(user_id, read_at)`, `activity_logs(entity_type, entity_id)`, `git_activities(repository_id, external_id)`, `refresh_tokens(jti)`.

### Ограничения целостности

- Удаление проекта — soft-delete; каскадное физическое удаление только для записей учёта времени и связей технологий.
- `due_date` задачи не может быть раньше `start_date`.
- Статус `is_final = true` (Done) проставляет `completed_at`; любой другой статус его снимает.

## 8. Критерии готовности проекта

1. Проект разворачивается одной командой на чистой машине, миграции применяются автоматически.
2. Все обязательные модули (1–8) работают и проверены вручную по чек-листу.
3. Автотесты покрывают: регистрацию и вход, ротацию refresh-токена, разграничение доступа между двумя пользователями, CRUD задач, расчёт прогресса с подзадачами, перемещение задачи по доске.
4. Демонстрационные данные соответствуют макету: 5–6 проектов, не менее 20 задач, 8 технологий, дедлайны в пределах месяца.
5. Разделение данных подтверждено тестом: пользователь A не может прочитать или изменить ни один объект пользователя B.
6. Готовы: пояснительная записка, ER-диаграмма, схема архитектуры, презентация и демонстрационные скриншоты всех экранов.

## 9. Ограничения и допущения

- Система однопользовательская: роли, приглашения и совместная работа не реализуются.
- Уведомления только внутрисистемные, без email и push.
- Интеграция с GitHub — только чтение; запись в репозиторий, вебхуки и Actions не затрагиваются.
- ИИ-помощник — демонстрационная функция, результат требует подтверждения пользователем.
- Даты в макете (2024 год) иллюстративны и не являются требованием к данным.
- Декоративные элементы макета (карточка с цитатой, предметы вокруг ноутбука) не входят в объём разработки.
